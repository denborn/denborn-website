# Security, trust boundaries and privacy

- Threat model: players may spoof GM messages, guess room codes, tamper with character JSON, replay actions, flood WebSocket frames, forge imports/QR, and script site UI. Every boundary validates both shape and authorization.
- Room lookup code is not a privilege token; provide a hard-to-guess ephemeral GM capability, never expose it in a player's sheet or share URL. No database is required to enforce connection-bound rights and GM-signed/verified session epochs.
- Use HTTPS and WSS. Check `Origin` at WebSocket upgrade for browser clients and **authorize each action** after handshake, not just connection. Bind sender identity/role to accepted connection metadata.
- Reject overlarge/rate-abusive frames, unauthorized commands, invalid enum variants and unknown protocol versions. No `eval`, dynamic JS execution, arbitrary HTML injection or unescaped rich text from saves.
- Use platform Web Crypto where signatures/tokens are needed, with stable audited primitives, no homemade encryption. Owner decision may be required on credential recovery.
- Don't put character content, GM tokens or campaign JSON in unauthenticated logs, URLs, error traces or analytics. Avoid collecting unneeded personal data (players can use nicknames).
- Offline-created character files are untrusted, even if generated by own app. Schema validation + allowed species/moves/stat budgets on import *and* session join.
- Never rely on UI disabled buttons to enforce game authority. Relay rejects actor forgery, GM engine rejects illegal intents.
- Verify supply-chain updates and sprite/data repository provenance; pin lockfiles; no runtime executable CDN packages.
